500 个 block：连续 Enter 实测

比较的是同一份专用 SQLite fixture、同一 API 33 arm64 模拟器、同一真实安装 App 的输入路径。每轮 15 次逐次输入（前 3 次预热，后 12 次计时），再以 20ms 间隔发送 20 次快速输入；核对 35 条连续 split intent 的落盘顺序、原文、光标和新 UUID。测量按键或原生输入法 action 到编辑框可用，直接读取当前 Compose 语义树，不含无障碍 IPC 遍历。fixture 数据库有 500 个既有 block；日记启动只加载前 32 行，Return 使用整页上下文。此次也修复了后台刷新把编辑页截回 32 行、丢失编辑器的问题。这里不声称已经测出完整像素呈现耗时或红米真机性能。

与 Swift 实现的区别：iOS 的虚拟列表专门保留 active editor 身份，UITextView 交接时保留 first responder，并保留等待期间的输入；Android 原先按行号标识编辑行，每次 Enter 会重建输入框，且从 text-change 猜测结构按键。本次对齐编辑器身份和交接原则，使用 Android 原生键盘 action / 硬件按键入口，并让编辑行保持可见。另一个独立问题来自共享日记的启动窗口：后台刷新曾截回 32 行，连续插入后编辑器会消失；现在刷新保留当前编辑页的完整结构，启动仍按需加载。共享 core 对正常相邻 split 复用完整页面读取结果，只重新读取受影响的内容与引用标签；非相邻或数据版本不匹配时仍走完整读取。嵌套顺序和引用/状态元数据与原始读取结果逐项对照。

输入法动作使用原生 Compose 键盘交互 API；普通多行粘贴和 Shift+Enter 仍按文本处理。没有增加第二套编辑器或修改 iOS 布局。

证据：enter-before.json · enter-after-key.json · enter-after-key-run1.json · enter-after-ime.json · enter-benchmark.py · verification-summary.json

最终空闲环境中，硬件 Enter 连续两轮通过（中位数 91 / 87ms），输入法 action 一轮通过（66.5ms）；三轮各 35 次拆分均按序持久化。曾有一轮与 core 测试并行运行出现 180ms 样本，故最终计时与构建/其他测试串行执行；不据模拟器数字外推真机。

12 个计时样本不足以代表各种设备与输入法的长期分布；p95 采用 nearest-rank，因此等于本轮最大值。红米体验仍需用对应真机版本验证，当前完成的是自动化模拟器专项。

P1 UX-01 · Android

已修复 · 正文长按进入块选择

当前：已修复并通过组件及真实 App 入口复测。以下为修改前的复现与截图；修复后证据见追加验收。

修改前复现：打开 journal，隐藏键盘，长按一行正文。先对含粗体、inline code 的现有块操作，再新建普通文本“UX review selection target”，滚动到正文可见后长按。

实际：两类正文都打开原生编辑器和键盘；没有出现 toolbar.outliner.selection。点击 bullet 则会 zoom，不能替代块选择入口。iOS 对正文相同手势会高亮块并显示 Copy / Outdent / Indent / Delete / Copy reference / Copy URL / Unselect。

影响：用户无法按预期进入批量块操作。独立工具栏测试证明按钮可渲染、可发事件，不能覆盖页面中的手势入口。子文本点击和父行长按的事件竞争值得后续排查，该描述保留原始只读审查边界；后续已确认子文本 click 抢占父级长按，并修复与复测。

验收：普通文本、富文本、任务块的正文长按均进入块选择；短按仍编辑，bullet 仍 zoom；工具栏出现后至少验证复制、取消选择和缩进的整条路径。

证据：android-plain-selection-repro.log · android-plain-selection-repro.csv · android-29-current-longpress.log · ios-editor-keyboard.log · ios-editor-keyboard.csv

P2 UX-02 · Android

已修复 · 新建 Graph 首次打开即可操作

当前：已修复并通过组件及真实 App 入口复测。以下为修改前的复现与截图；修复后证据见追加验收。

P1 UX-03 · Android

已修复 · Capture 背景、宽度与命中区域一致

当前：已修复并通过组件及真实 App 入口复测。以下为修改前的复现与截图；修复后证据见追加验收。

修改前复现：在包含图片的 journal 展开 composer，点外部收起；确认显示 Capture；点击底部 Capture 所在横向区域中部的空白处（本机约屏幕 55% / 92%）。

实际：打开图片图库，而非 Capture。底部只剩相机图标和较小的 outlined Capture 按钮，图片透到它们背后。可访问树中按钮宽约 84 dp，所在横向布局约 312 dp，视觉上的底部输入区没有形成一致的点击目标。

对照：iOS 用连续的输入面板明确区分页面内容与 Capture。Android 应用自己的 M3 surface 与合适的命中范围即可，无需照搬玻璃样式。

验收：统一底部可见边界、surface 和命中范围；背景为图片或深色内容时保持可读；面板区域内部空白不会触发下层内容；面板外的真实图片仍能进入图库。

07 · PLATFORM FIT

Native / M3 的边界

当前构建配置为 Compose BOM 2026.09.00、Material 3 1.5.0-beta01，minSdk 26 / targetSdk 36；本轮 Android UI 实测只覆盖 API 33。版本号来自仓库构建配置，不代表已验证所有新系统交互。

Android 菜单、对话框、输入框、开关与面板应使用当前 Material 3 组件；文件选择、照片选择、权限、分享、桌面快捷方式和通知栏 tile 则交给 Android 系统容器。iOS 使用自己的系统菜单、表单与键盘。相同功能不要求两个平台使用相同外观。

Compose 官方菜单文档介绍 DropdownMenu / DropdownMenuItem / IconButton，官方 Bottom sheet 文档提供 ModalBottomSheet。当前采用这些原生组件不代表组合后的点击、焦点、留白与可达性自动正确。UX-02 与 UX-03 正是这类整页集成问题。菜单视觉评审参照用户提供的 Material 3 menus，本报告不作像素级全规范认证。

Composer 没有一颗能覆盖本产品所有行为的现成“native composer”。它需要由原生输入、按钮、菜单和 surface 组合；编辑器工具栏也需要表达应用的块操作。后续应修正现有组合的行为，保持实现简单，不为统一外观引入第二套组件系统。
